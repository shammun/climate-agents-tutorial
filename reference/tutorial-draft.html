#Introduction

In this tutorial we learn what an AI agent is, what a subagent is, and how to build a small team of agents that analyse climate data. We first look at agents in general, in a way that does not depend on any one product. Then we build a complete working example step by step in Claude Code, and finally we see how the same agents are written for other AI coding tools.

The running example is a simple research question:

Question: Has summer (June–August) near-surface air temperature over Virginia warmed between 1991 and 2024?

Five agents answer it together. One downloads ERA5 data, one checks the data, one computes the trend, one draws the figures and one reviews the result.

Every file shown here is part of a template that can be downloaded and changed for other projects.

#What is needed

  • An AI coding tool that runs in a terminal. The step-by-step part uses Claude Code. Part 3 shows OpenAI Codex, Gemini CLI and GitHub Copilot.
  • A text editor, for example VS Code.
  • For the climate example only: Python with xarray, and a free Copernicus Climate Data Store (CDS) account to download ERA5 data.

No programming is needed to write agents. Agents are plain text files.

#Part 1 — Agents in general

#1. What an agent is

A large language model (LLM) is a program that reads text and writes text. On its own it can only answer. It cannot open a file or run a script.

An agent is an LLM that can also take actions. It is built from four parts:

  1. A model — the LLM that reads the situation and decides what to do next.
  2. Instructions — text that tells the model its role, its rules and what a good answer looks like. This text is often called the system prompt.
  3. Tools — ordinary functions the model is allowed to ask for, such as "read a file", "run a Python script" or "search the web".
  4. A loop — a small program that runs the tool the model asked for, gives the result back to the model, and repeats until the model gives a final answer.

Here is the loop in words, with a climate task:

  1. The task arrives: "Check the file era5_t2m.nc."
  2. The model decides: "I need to see what is in the file. Call the tool inspect_file."
  3. The loop runs inspect_file and sends the result back: "units = K, 2 % missing values …".
  4. The model decides: "I have enough information. Final answer: the file is usable, but 2 % of values are missing."

The model never touches the file itself. It only asks, and the loop does the work. This is why the choice of tools is also a choice of what an agent is allowed to do.

The text an agent can see at one moment is called its context. This is the instructions, the task and every tool result so far. The context has a size limit, and a long, cluttered context makes answers worse. This one fact explains most of the design advice in this tutorial.

#2. What a subagent is

A subagent is an agent that another agent calls, in the same way it calls a tool. The calling agent is the main agent, sometimes called the orchestrator.

A research group is a useful comparison. The main agent is the lead researcher who talks to you. The subagents are specialists: one handles data downloads, one does quality control, one does statistics.

Subagents help for three reasons:

  • A clean context. A subagent starts with an empty context. It may read fifty files, but only its short summary comes back to the main agent, so the main conversation stays clean.
  • Specialisation. Each subagent has its own instructions, so it can hold detailed rules for one job.
  • Safety. Each subagent has its own tool list. A checking agent can be given read-only tools, so it can look at data but never change it.

Subagents also cost something. Each one starts from zero, so the main agent must pass every needed detail (file paths, decisions) in its request. Each one also uses extra time and tokens. A token is a small piece of text, about three quarters of a word, and AI usage is counted in tokens. For a small task it is usually better not to delegate.

#3. An agent in plain Python

To see that nothing here is magic, here is a complete agent and subagent in about 100 lines of Python. It uses no AI product. A small scripted function stands in for the model, so the file runs offline. To use a real model, replace the body of call_model() with a call to any provider's chat API that supports tool calling.

examples/minimal_agent.py
"""A minimal agent and subagent, written without any AI tool or framework.

An agent is four things:
  1. a model         - something that reads messages and decides what to do next
  2. instructions    - the system prompt (the "rules")
  3. tools           - ordinary functions the model may ask to run
  4. a loop          - run the tool the model asked for, give it the result, repeat

A subagent is simply an agent that another agent calls as if it were a tool.

This file runs offline with Python only:  python examples/minimal_agent.py
The "model" here is a small scripted stand-in so the loop can be seen working.
To use a real model, replace the body of call_model() with a call to any
provider's chat API that supports tool calling, and keep everything else.
"""
import csv
import json
from pathlib import Path

HERE = Path(__file__).parent


class="hl-c"># ---------------------------------------------------------------- tools
def list_files(folder):
    """Return the names of files in a folder."""
    return sorted(p.name for p in (HERE / folder).iterdir() if p.is_file())


def summarize_csv(path):
    """Return count, min, mean, max of the 'tas_C' column and how many values are -999 (missing)."""
    values = [float(row["tas_C"]) for row in csv.DictReader(open(HERE / path))]
    good = [v for v in values if v != -999]
    return {"rows": len(values), "missing": len(values) - len(good),
            "min": min(good), "mean": round(sum(good) / len(good), 2), "max": max(good)}


class="hl-c"># ---------------------------------------------------------------- the model (replace this)
def call_model(system_prompt, messages, tool_names):
    """Decide the next action. Returns {"tool": name, "args": {...}} or {"final": text}.

    A real version sends system_prompt, messages and the tool descriptions to an LLM
    and converts its reply into this same dictionary. This stand-in follows a fixed script.
    """
    results = [m for m in messages if m["role"] == "tool"]
    if "summarize_csv" in tool_names:                      class="hl-c"># behaving as the QC subagent
        if not results:
            return {"tool": "list_files", "args": {"folder": "."}}
        if len(results) == 1:
            csv_name = next(n for n in json.loads(results[0]["content"]) if n.endswith(".csv"))
            return {"tool": "summarize_csv", "args": {"path": csv_name}}
        s = json.loads(results[1]["content"])
        status = "PASS" if s["missing"] == 0 and -60 < s["min"] and s["max"] < 60 else "NEEDS ATTENTION"
        return {"final": f"QC of {s['rows']} rows: {s['missing']} missing (-999), "
                         f"range {s['min']}..{s['max']} °C. OVERALL: {status}"}
    else:                                                  class="hl-c"># behaving as the main agent
        if not results:
            return {"tool": "ask_qc_agent", "args": {"task": "Check the station CSV file in this folder."}}
        return {"final": "The QC helper reported: " + results[0]["content"]}


class="hl-c"># ---------------------------------------------------------------- the loop
def run_agent(name, system_prompt, tools, task, max_turns=8):
    messages = [{"role": "user", "content": task}]
    for turn in range(1, max_turns + 1):
        action = call_model(system_prompt, messages, list(tools))
        if "final" in action:
            print(f"[{name}] final answer: {action['final']}")
            return action["final"]
        print(f"[{name}] turn {turn}: calls {action['tool']}({action['args']})")
        result = tools[action["tool"]](**action["args"])
        messages.append({"role": "tool", "content": json.dumps(result) if not isinstance(result, str) else result})
    return "Stopped: turn limit reached."


class="hl-c"># ---------------------------------------------------------------- a subagent = an agent used as a tool
QC_PROMPT = "You are a data quality checker. Inspect files and report problems. Never change files."
QC_TOOLS = {"list_files": list_files, "summarize_csv": summarize_csv}


def ask_qc_agent(task):
    """Tool for the main agent: starts the QC subagent with a fresh, empty conversation."""
    return run_agent("qc-subagent", QC_PROMPT, QC_TOOLS, task)


MAIN_PROMPT = "You are the lead analyst. Delegate quality checks to the QC helper."
MAIN_TOOLS = {"ask_qc_agent": ask_qc_agent}

if __name__ == "__main__":
    run_agent("main-agent", MAIN_PROMPT, MAIN_TOOLS, "Is the station data ready for analysis?")

Running it with python examples/minimal_agent.py prints every step:

text
[main-agent] turn 1: calls ask_qc_agent({'task': 'Check the station CSV file in this folder.'})
[qc-subagent] turn 1: calls list_files({'folder': '.'})
[qc-subagent] turn 2: calls summarize_csv({'path': 'sample_station.csv'})
[qc-subagent] final answer: QC of 24 rows: 1 missing (-999), range 1.3..25.2 °C. OVERALL: NEEDS ATTENTION
[main-agent] final answer: The QC helper reported: QC of 24 rows: 1 missing (-999), range 1.3..25.2 °C. OVERALL: NEEDS ATTENTION

Three things to notice:

  • The subagent is just run_agent() wrapped in a function (ask_qc_agent) that the main agent can call as a tool.
  • The subagent starts with a new, empty message list. It does not see the main agent's conversation.
  • Only the subagent's final answer goes back to the main agent. Its intermediate steps stay inside it.

AI coding tools such as Claude Code, Codex and Gemini CLI run this same loop for you. What you write is the part that changes from project to project: the instructions, the tool lists and the reusable knowledge. These are written as text files.

#4. The building blocks every tool shares

Most AI coding tools now use the same four kinds of files. The names and folders differ, but the ideas are the same.

Building blockWhat it isLoaded whenExamples
Project rules fileA briefing sheet for the whole project: folders, environment, "always" and "never" rulesAt the start of every sessionAGENTS.md (open standard), CLAUDE.md, GEMINI.md
Agent definitionOne specialist: its role, tools, model and instructionsWhen the main agent delegates a task to it.claude/agents/*.md, .codex/agents/*.toml, .gemini/agents/*.md, .github/agents/*.agent.md
SkillA reusable manual or procedure, with optional helper scriptsOnly when a task needs itA folder with a SKILL.md file (open Agent Skills standard)
PermissionsHard limits on what any agent may doAlways enforced.claude/settings.json, Codex sandbox settings

Two of these are open standards, which means many tools read the same file:

  • AGENTS.md is a plain Markdown file of project instructions. It started at OpenAI and is now managed by the Agentic AI Foundation under the Linux Foundation. Codex, GitHub Copilot, Cursor and many other tools read it.
  • Agent Skills (SKILL.md) is a folder format for reusable knowledge. Anthropic created it and published it as an open standard at agentskills.io, and dozens of tools support it.

The template in this tutorial uses both. The project rules are in AGENTS.md, and CLAUDE.md simply imports it. The skills follow the open standard, so they can be reused in other tools.

#5. How to design a team of agents

These rules apply in every tool.

  1. One clear job per agent. "Checks data quality" is a job. "Helps with climate stuff" is not.
  2. Write the trigger, not just the role. The main agent picks a subagent by reading its description. Say what it does and when to use it: "Use after any new file is downloaded."
  3. Give the fewest tools that work. A checker or reviewer should be read-only. Then it cannot "fix" data quietly.
  4. Fix the output format. A table, a PASS/FAIL line, a list of file paths. The main agent reads the answer, so a fixed shape makes the handoff reliable.
  5. Use a fresh agent to review. An agent that did the work tends to approve its own work. A reviewer that starts from a clean context finds more problems.
  6. Put shared knowledge in one place. If two agents need the same rule, put it in the project rules file or a skill, not in both agent files.
  7. Start small. Begin with one or two agents. Add another only when the same instructions keep being typed again.

#7. Reading and writing YAML frontmatter

Agent files and skill files start with a short settings block called frontmatter. It is written in YAML, a simple format of labels and values.

The rules, from simplest to less simple:

The block. The very first line of the file is exactly three hyphens, ---. The settings follow, one per line. Another --- line closes the block. Everything after it is the body: normal Markdown text.

A setting is a key, a colon, one space, and a value:

yaml
name: data-qc
model: sonnet

The key on the left must be spelled exactly as the tool expects, in lowercase. The value on the right is your choice.

A long sentence stays on one line, however long. The editor may wrap it on screen. That is fine, as long as Enter is not pressed in the middle.

yaml
description: Checks NetCDF climate files for missing values, wrong units and bad coordinates. Use after any download.

A value with a colon inside goes in quotes:

yaml
description: "Checks data. Note: read-only."

A list can be written in two equivalent ways. Comma-separated on one line:

yaml
tools: Read, Grep, Glob, Bash

Or one item per line, each line starting with two spaces, a hyphen and a space:

yaml
skills:
  - netcdf-conventions
  - era5-download

Yes/no values are written true or false.

Common mistakes:

MistakeWrongRight
No space after the colonmodel:sonnetmodel: sonnet
A tab before a list item⇥- item - item (two spaces)
Capital letters in a keyTools: Readtools: Read
Blank line before the first ---(empty line), then ------ on line 1
Windows Notepad adds .txtdata-qc.md.txtIn "Save as type" choose "All files"

#8. Step 1 — The project rules: AGENTS.md and CLAUDE.md

The project rules file is the briefing sheet for the whole project. It is read automatically at the start of every session, and every subagent receives it too. It has no frontmatter. It is plain Markdown: headings with #, bullet points with -, and code in backticks.

The template keeps the shared rules in AGENTS.md, so any tool that reads the open standard can use them:

AGENTS.md
# Climate Analysis Project

Shared instructions for any AI coding agent working in this folder
(Claude Code, Codex, Gemini CLI, GitHub Copilot, Cursor and others).

## What this project is
A climate data analysis project. The worked example asks one question:
has summer (June–August) near-surface air temperature over Virginia warmed since 1991?
Data source: ERA5 monthly means (2 m temperature), 1991–2024.

Change this section to describe your own project.

## Folder layout
- data/raw/        — downloaded files. NEVER modify, move or delete anything here.
- data/processed/  — derived NetCDF files written by analysis scripts
- scripts/         — all code, numbered in run order: 01_download.py, 02_qc.py, 03_jja_mean.py, ...
- figures/         — figures as PNG (300 dpi) and PDF
- reports/         — QC reports and short Markdown summaries of results
- hpc_jobs/        — SLURM job scripts for long runs on a cluster

## Environment
- Python environment: `conda activate climate` (see environment.yml)
- Core libraries: xarray, netCDF4, dask, numpy, scipy, statsmodels, matplotlib, cartopy, cdsapi
- Run a script from the project root: `python scripts/03_jja_mean.py`

## Workflow
1. Download data          (data-fetcher)
2. Check data quality     (data-qc) — save each QC report to reports/qc_<file-name>.md
3. Compute statistics     (climate-analyst)
4. Make figures           (figure-maker)
5. Independent review     (results-reviewer)
When handing a step to a helper agent, pass full file paths: helpers do not see the main conversation.

## Always
- Write every step as a script in scripts/, never as a one-off command, so it can be re-run.
- Area-weight spatial means with cos(latitude).
- Convert longitude to -180..180 before selecting a region.
- State units for every number, axis and colorbar.
- State the baseline period for every anomaly (default 1991–2020).

## Never
- Never edit, overwrite or delete files in data/raw/.
- Never put API keys or passwords in scripts or in this file.
- Never run a job longer than about 30 minutes locally; write a SLURM script in hpc_jobs/ instead.

Claude Code reads a file called CLAUDE.md. A line containing only @ and a file name, such as @AGENTS.md, imports that file, which means its text is pulled in at that point. So CLAUDE.md can stay short and add only the parts that are specific to Claude Code:

CLAUDE.md
# Claude Code instructions

The shared project rules live in AGENTS.md (read by many AI coding tools).
The next line imports them so Claude Code reads them too:

@AGENTS.md

## Claude Code only
- Subagents for each workflow step are in .claude/agents/:
  data-fetcher, data-qc, climate-analyst, figure-maker, results-reviewer.
- Skills are in .claude/skills/. Run the whole workflow with: /run-climate-pipeline <question>
- data-qc and results-reviewer are read-only. When data-qc returns a report, save it to
  reports/qc_<file-name>.md before starting the analysis step.

Where the file can live:

LocationApplies to
your-project/CLAUDE.md (top level of the project)This project. This is the main one.
~/.claude/CLAUDE.mdAll your projects (personal habits)
your-project/some-folder/CLAUDE.mdExtra rules, loaded when work happens in that folder

How to write a good one:

  • Keep it short. Aim for under about 200 lines. It is loaded in every session, and important rules get lost in a long file.
  • Write facts and rules, not essays. Bullets work better than paragraphs.
  • Be specific. "Use the conda environment climate" is better than "use the right environment."
  • Use "Always" and "Never" lists.
  • Move long procedures into skills.
  • Get a first draft for free. Run /init inside Claude Code. It writes a draft by looking at the project, which can then be edited.
  • Grow it over time. When an agent makes the same mistake twice, add a rule.

#9. Step 2 — Skills: reusable knowledge

An agent is a worker (the "who"). A skill is a manual (the "how"). Any agent, including the main one, can use a skill.

A skill is a folder, not a single file. Inside it there must be a file named exactly SKILL.md. The folder can also hold helper scripts and reference files.

When a session starts, Claude Code reads only the name and description of each skill, so many skills cost very little. The full text is loaded only when a task needs it. This is called progressive disclosure: details are shown only when needed.

A SKILL.md has the same layout as an agent file: frontmatter, then body. Only name and description are required. The name should match the folder name.

#Skill 1: netcdf-conventions — knowledge used by several agents

.claude/skills/netcdf-conventions/SKILL.md
---
name: netcdf-conventions
description: Project conventions for reading, checking and writing climate NetCDF files (coordinate names, longitude convention, units, calendars, attributes). Use whenever code opens or writes a .nc file.
---

# NetCDF conventions for this project

## Opening files
- Open with `xr.open_dataset(path)`; for files larger than 2 GB use `chunks={"time": 12}`.
- To get a quick summary of any file, run the helper:
  `python .claude/skills/netcdf-conventions/scripts/inspect_nc.py <file>`

## Coordinate names
Rename coordinates right after opening, so every script sees the same names:

| Found in file              | Rename to |
|----------------------------|-----------|
| latitude, nav_lat, y (deg) | lat       |
| longitude, nav_lon, x (deg)| lon       |
| valid_time (ERA5 from CDS) | time      |

- Latitude must increase (south to north). If it decreases, use `ds.sortby("lat")`.

## Longitude
- Convert to -180..180 before selecting a region:
  `ds = ds.assign_coords(lon=((ds.lon + 180) % 360) - 180).sortby("lon")`

## Units
| Variable              | Raw unit in ERA5     | Unit used in this project | Conversion |
|-----------------------|----------------------|---------------------------|------------|
| 2 m temperature (t2m) | K                    | °C                        | subtract 273.15 |
| total precipitation   | m (accumulated)      | mm/day                    | multiply by 1000; for monthly means the value is already per day |
| 10 m wind (u10, v10)  | m s-1                | m s-1                     | none |

Always update the `units` attribute after a conversion.

## Calendars
- ERA5 and most observations: standard (Gregorian) calendar.
- Many CMIP6 models: `noleap` or `360_day`. Open them with `use_cftime=True`.
- Never subtract or merge time axes from different calendars without converting first
  (`ds.convert_calendar("standard", align_on="date")`).

## Writing files
Every NetCDF written to data/processed/ must have, for each variable:
- `units` and `long_name`
- a global `history` attribute naming the script that wrote it, for example
  `ds.attrs["history"] = "written by scripts/03_jja_mean.py"`

This skill comes with a helper script, scripts/inspect_nc.py, which prints a quick summary of any NetCDF file. The data-qc agent runs it. A skill can carry tested code, so agents do not rewrite it every time.

#Skill 2: era5-download — a procedure with a helper script

.claude/skills/era5-download/SKILL.md
---
name: era5-download
description: How to download ERA5 reanalysis data from the Copernicus Climate Data Store (CDS) with the cdsapi package, including the helper script, request format, variable names and units. Use whenever ERA5 data is needed.
---

# Downloading ERA5 data

## Before the first download
1. A free CDS account and its API key are needed. The key goes in the file `~/.cdsapirc`:
   ```
   url: https://cds.climate.copernicus.eu/api
   key: <your-personal-access-token>
   ```
2. The dataset licence must be accepted once on the dataset's web page on the CDS site.
3. If `~/.cdsapirc` does not exist, stop and ask the user to create it. Never write the key yourself.

## Use the helper script
Monthly means (small, fast — the default):
```
python .claude/skills/era5-download/scripts/download_era5.py \
    --variable 2m_temperature --start 1991 --end 2024 \
    --area 39.5 -83.7 36.5 -75.2 --name virginia --outdir data/raw/era5
```
- `--area` order is North West South East, in degrees.
- The script sends one request per year and skips years whose file already exists.
- Add `--hourly` for hourly data (much larger; consider fewer years).

## Common variables
| CDS request name          | Short name in file | Unit |
|---------------------------|--------------------|------|
| 2m_temperature            | t2m                | K    |
| total_precipitation       | tp                 | m (monthly means: m per day) |
| 10m_u_component_of_wind   | u10                | m s-1 |
| 10m_v_component_of_wind   | v10                | m s-1 |
| skin_temperature          | skt                | K    |

## Things to watch
- Files from the current CDS name the time coordinate `valid_time`. Rename it to `time`.
- Recent months can carry an `expver` coordinate (preliminary data). Note it in SOURCE.md.
- Requests are queued on the CDS side; a request can wait several minutes before it starts.

#Skill 3: climate-figure-style — a house style

.claude/skills/climate-figure-style/SKILL.md
---
name: climate-figure-style
description: House style for climate figures — colormaps, labels, map projection, sizes, fonts and file names. Use whenever a plot or map is made.
---

# Climate figure style

## Colormaps
| What is shown                       | Colormap | Notes |
|-------------------------------------|----------|-------|
| Anomalies, trends (can be + or −)   | RdBu_r   | Centre on zero: `TwoSlopeNorm(vcenter=0)` |
| Absolute temperature                | viridis or magma | |
| Precipitation amount                | YlGnBu   | |
| Precipitation anomaly               | BrBG     | Centre on zero |

Never use rainbow or jet.

## Maps
- Projection: `ccrs.PlateCarree()` for small regions; `ccrs.Robinson()` for global maps.
- Always add coastlines and state or country borders (`cfeature.STATES` for the US).
- Mark grid cells with a significant trend (p < 0.05) with small dots (stippling).

## Labels
- Every axis and colorbar label has units in brackets, for example `Trend [°C per decade]`.
- Title format: `<variable>, <season> <period>`, for example `2 m temperature trend, JJA 1991–2024`.
- Source line in the bottom-left corner, font size 7: `Data: ERA5 (Copernicus C3S)`.

## Size and files
- Single-column figure: 3.5 in wide; full-width figure: 7 in wide. Font size 9.
- Save both `figures/<topic>_<variable>_<type>.png` (dpi=300) and the same name as `.pdf`.
- Use `bbox_inches="tight"` so nothing is cut off.

#Skill 4: run-climate-pipeline — a command started by hand

Some skills are workflows that should run only when you ask. The setting disable-model-invocation: true stops Claude from starting it on its own. The skill then works like a command: type /run-climate-pipeline followed by the question. The text after the command replaces $ARGUMENTS in the skill.

.claude/skills/run-climate-pipeline/SKILL.md
---
name: run-climate-pipeline

disable-model-invocation: true
argument-hint: "[research question]"
---

# Run the climate pipeline

Research question: $ARGUMENTS

Work through these steps in order. Hand each step to the named subagent and pass it full file paths.
After each step, show a two-line summary to the user before continuing.

1. **Download** — ask the data-fetcher subagent for the data the question needs.
2. **Quality check** — ask the data-qc subagent to check every new file.
   Save each report to reports/qc_<file-name>.md.

5. **Review** — ask the results-reviewer subagent to check steps 3 and 4.

Finish with a short summary: the answer to the question in one or two sentences,
the key numbers with units, and the paths of the figures.

#10. Step 3 — Agents: the specialists

Each agent is one Markdown file in .claude/agents/. The file name does not have to match the name field, but keeping them the same avoids confusion.

#The frontmatter fields

FieldRequiredWhat it does
nameYesThe agent's ID: lowercase letters and hyphens, for example data-qc
descriptionYesWhen the main agent should use it. The most important line.
toolsNoThe tools it may use, for example Read, Grep, Glob, Bash. If left out, it gets every tool.
disallowedToolsNoTools to take away, for example Write, Edit
modelNosonnet, opus, haiku, a full model ID, or inherit (same as the main session)

memoryNoproject, user or local: gives the agent a folder of notes that survives between sessions
maxTurnsNoThe most steps the agent may take before it stops
effortNoHow hard the model thinks: low, medium, high, xhigh, max
colorNoIts colour in the task list, for example blue

The tools used most often:

ToolWhat it does
ReadRead a file (also images, so an agent can look at its own figures)

BashRun a terminal command, for example python scripts/03_trend.py

#Writing the description

The main agent compares the task with every agent's description and picks one. So write the description like a rule for choosing: what it does, plus when to use it.

Too vague:

yaml
description: Helps with climate data.

Clear:

yaml
description: Checks NetCDF or GRIB climate files for quality problems (missing values, units, coordinates, calendars, time gaps) before analysis. Use proactively after any download, regrid or merge. Read-only; it reports problems and never fixes them.

The words "use proactively" make the main agent more likely to call the agent without being asked.

#Writing the body

The body is the agent's whole set of instructions. Apart from the project rules file, it knows nothing else. A good order:

markdown
You are a [ROLE].                      ← 1. who it is, in one line

## Your job                            ← 2. what it does, and what it does NOT do
## Inputs you will receive             ← 3. what the main agent will hand over
## Procedure                           ← 4. numbered steps
## Rules                               ← 5. always / never
## Output format                       ← 6. exactly what to return

Write it as a briefing for a new research assistant. Be concrete: "check units" is weak, while "a mean 2 m temperature above 200 means Kelvin" is strong.

#The five agent files

data-fetcher — downloads data and records where it came from. It preloads the era5-download skill.

.claude/agents/data-fetcher.md
---
name: data-fetcher
description: Downloads and subsets climate datasets (ERA5 from the Copernicus Climate Data Store, CMIP6, satellite products) into data/raw/. Use when a task needs data that is not yet in data/raw/.
tools: Read, Write, Edit, Bash, Glob
model: sonnet
skills:
  - era5-download
color: blue
---

You are a climate data acquisition specialist.

## Your job
Get the requested data into data/raw/ and record where it came from.
You do NOT analyse, regrid or plot data.

## Inputs you will receive
- The dataset, variable(s), years and region (as a North/West/South/East box).

## Procedure
1. Look in data/raw/ with Glob first. Never download a file that already exists.
2. For ERA5, follow the preloaded era5-download skill and use its helper script.
   For any other source, write a download script in scripts/ (for example 01_download_cmip6.py).
3. Subset at the source (region, years, variables) whenever the source allows it.
4. After the download, write data/raw/<dataset>/SOURCE.md with: source, dataset name,
   variables, years, region, download date and the script that was used.

## Rules
- Never put API keys in scripts. Credentials live in ~/.cdsapirc or environment variables.
- File names: <dataset>_<variable>_<region>_<startyear>-<endyear>.nc
- If the estimated download is larger than 20 GB, stop and report the size instead of downloading.

## Output format
- Files created (full paths) and their sizes
- The script used
- Any failed requests, with the error message

data-qc — read-only checker. disallowedTools: Write, Edit makes sure it cannot change anything.

.claude/agents/data-qc.md
---
name: data-qc
description: Checks NetCDF or GRIB climate files for quality problems (missing values, units, coordinates, calendars, time gaps) before analysis. Use proactively after any download, regrid or merge. Read-only; it reports problems and never fixes them.
tools: Read, Bash, Grep, Glob
disallowedTools: Write, Edit
model: sonnet
skills:
  - netcdf-conventions
color: yellow
---

You are a climate data quality-control specialist. You inspect files; you never change them.

## Inputs you will receive
One or more file paths, or a folder path.

## Procedure
For each file, run the inspection helper from the netcdf-conventions skill:
`python .claude/skills/netcdf-conventions/scripts/inspect_nc.py <file>`
Then check:
1. Coordinates: names (lat/latitude, lon/longitude, time), order, and that they are monotonic.
2. Longitude convention: 0..360 or -180..180. Report which one.
3. Units: compare the `units` attribute with the actual values.
   A mean 2 m temperature above 200 means Kelvin.
4. Time: calendar type (standard, noleap, 360_day), gaps, duplicate time steps.
5. Missing values: fraction of NaN per variable, and whether _FillValue is set.
6. Physical sanity: values outside plausible ranges
   (for example 2 m temperature below 180 K or above 340 K).

## Rules
- Never write or edit any file. Never "fix" anything. Only report.
- For files larger than 2 GB, open them lazily with dask chunks; never load the full array.

## Output format
One table per file:

| Check | Status (PASS / WARN / FAIL) | Detail |

End with one line: `OVERALL: PASS` or `OVERALL: NEEDS ATTENTION — <the most important issue>`.
Return the full report as your answer; the main agent saves it to reports/.

climate-analyst — does the statistics. memory: project gives it a notes folder (.claude/agent-memory/climate-analyst/) that survives between sessions, so it can remember dataset quirks.

.claude/agents/climate-analyst.md
---
name: climate-analyst
description: Runs climate statistics on data that has passed QC — climatologies, seasonal means, anomalies, trends, area-weighted means, extremes indices. Use for any computation step after data-qc reports OVERALL PASS.
tools: Read, Write, Edit, Bash, Glob, Grep
model: opus
skills:
  - netcdf-conventions
memory: project
color: green
---

You are a climate data scientist who works with xarray, dask, numpy, scipy and statsmodels.

## Your job
Turn quality-checked data into numbers and derived datasets.
Every result must be reproducible from a script in scripts/.

## Inputs you will receive
- Input file paths and the question to answer (for example "JJA trend 1991–2024").

## Procedure
1. Read the QC report for each input file in reports/. If it does not say OVERALL: PASS, stop and say so.
2. Write the analysis as a numbered script in scripts/. Start the script with a comment block
   that lists inputs, outputs and method.
3. Run the script. Save derived data to data/processed/ as NetCDF with units, long_name and history attributes.
4. Print a short numeric summary at the end of the script, and save it to reports/<script-name>_summary.md.

## Rules
- Spatial means must be area-weighted with weights = cos(latitude).
- State the baseline period for every anomaly (default 1991–2020).
- Trends: give the slope in units per decade, the p-value, and say how autocorrelation was handled
  (for example a Mann-Kendall test with prewhitening, or an effective sample size).
- Never drop NaN values silently. Report how many values were excluded.
- Long jobs (more than about 30 minutes or 32 GB of memory) go to a SLURM script in hpc_jobs/.

## Memory
Your project memory folder keeps notes between sessions. Record dataset quirks you discover
(for example "ERA5 2 m temperature is in K") so later runs avoid the same problem.

## Output format
- Scripts written and output files (full paths)
- Key numbers in a small table, with units
- Caveats, one bullet each

figure-maker — draws figures in the house style and looks at each PNG before reporting back.

.claude/agents/figure-maker.md
---
name: figure-maker
description: Makes publication-quality maps and plots of climate results (cartopy maps, time series, anomaly panels). Use after climate-analyst has written output files to data/processed/.
tools: Read, Write, Edit, Bash, Glob
model: sonnet
skills:
  - climate-figure-style
color: purple
---

You are a scientific visualisation specialist for climate figures.

## Inputs you will receive
- Paths of processed NetCDF files and what each figure should show.

## Procedure
1. Write a plotting script in scripts/ (for example 05_figures.py). Never plot from a one-off command.
2. Follow the preloaded climate-figure-style skill for colours, labels, sizes and file names.
3. Save every figure as PNG (300 dpi) and PDF in figures/.
4. Open each PNG with the Read tool and look at it. Fix overlapping labels, cut-off text
   or a missing colorbar before you report back.

## Rules
- Every axis and every colorbar has a label with units.
- Do not change any numbers. If a value looks wrong, report it instead of "fixing" the plot.

## Output format
- Figure paths
- One sentence per figure saying what it shows

results-reviewer — an independent, read-only check in a fresh context.

.claude/agents/results-reviewer.md
---
name: results-reviewer
description: Independently checks analysis scripts, numbers and figures for scientific and coding errors, in a fresh context. Use proactively before results go into a paper, report or presentation.
tools: Read, Grep, Glob, Bash
disallowedTools: Write, Edit
model: opus
color: red
---

You are a careful co-author reviewing someone else's climate analysis. You did not write it.

## Inputs you will receive
- The scripts, output files and figures to review.

## Check for
- Spatial means that are not area-weighted.
- A wrong or unstated baseline period.
- Unit mix-ups: K vs °C, metres vs millimetres of precipitation, per second vs per day.
- Calendar mistakes when combining model data (noleap, 360_day) with observations (standard).
- Longitude convention mismatches when selecting a region.
- Trend significance claimed without accounting for autocorrelation.
- Numbers in reports/ that do not match the script output. Re-run the summary part of a script to confirm.

## Rules
- Do not edit any file. Report only.
- Quote the exact file and line for every finding.

## Output format
Findings ranked CRITICAL, MAJOR or MINOR. For each: file:line, the problem, and a one-line fix.
End with: `VERDICT: READY` or `VERDICT: NOT READY — <main reason>`.

#11. Step 4 — Permissions: hard limits

Rules in text files are guidance. The model follows them well, but they are not a guarantee. For things that must never happen, use permissions in .claude/settings.json. Claude Code enforces these whatever the instructions say.

.claude/settings.json
{
  "permissions": {
    "deny": [
      "Edit(./data/raw/**)",
      "Read(~/.cdsapirc)"
    ],
    "ask": [
      "Bash(rm *)"
    ]
  }
}
  • deny — always blocked. Here: editing anything in data/raw/, and reading the file that holds the CDS key.
  • ask — Claude Code asks you first. Here: any rm (delete) command.
  • allow — runs without asking (not used in this template).

#12. Step 5 — Running the team

#Create the files

There are three ways to create agent and skill files:

  1. Download the template and copy its folders into a project.
  2. Ask Claude Code to write one, for example: "Create a subagent in .claude/agents/data-qc.md that checks NetCDF files, is read-only and uses sonnet." Then open the file and check it.
  3. Write it by hand in any editor. On Linux or macOS:
bash
mkdir -p .claude/agents
nano .claude/agents/data-qc.md

On Windows PowerShell:

powershell
mkdir .claude\agents -Force
notepad .claude\agents\data-qc.md

Claude Code notices new and changed agent files within seconds. One exception: if the agents folder did not exist when the session started, restart Claude Code once.

#Call the agents

WayExample
Automatically"Download ERA5 2 m temperature for Virginia, 1991–2024." The main agent picks data-fetcher from its description.
By name"Use the data-qc agent to check every file in data/raw/era5/."
With an @-mentionType @, choose the agent, then the task. Or type @agent-data-qc.
As the main agent for a whole sessionclaude --agent data-qc
The whole pipeline/run-climate-pipeline Has summer (JJA) 2 m temperature over Virginia warmed between 1991 and 2024?

#What happens, step by step

  1. Session start. Claude Code reads CLAUDE.md (which pulls in AGENTS.md), plus the name and description of every agent and skill.
  2. /run-climate-pipeline … loads that skill's full text. The question replaces $ARGUMENTS.
  3. data-fetcher starts in a fresh context with its instructions, the project rules and the era5-download skill. It runs the helper script and writes data/raw/era5/ plus SOURCE.md, then returns a list of files.
  4. data-qc runs inspect_nc.py on every file and returns a PASS/FAIL table. The main agent saves it in reports/. If something fails, the pipeline stops and shows the problem.
  5. climate-analyst writes scripts/03_jja_trend.py, runs it and saves the results in data/processed/ and reports/.
  6. figure-maker writes the plotting script, saves the PNG and PDF files, opens the PNGs and fixes any layout problems.
  7. results-reviewer checks the scripts and numbers in a clean context and returns READY or NOT READY.
  8. The main agent gives the answer: the trend in °C per decade, its p-value, and the figure paths.

Things worth knowing:

  • Subagents can run in parallel when tasks do not depend on each other, for example checking ten files at once.
  • A subagent can start its own subagents, by default up to three levels below the main conversation.
  • If the main agent does not pick an agent you expected, make that agent's description more specific, or call it by name.

#14. Building agents in code

AI coding tools are agents for working in a folder of files. To build an agent into your own program, for example a web service that answers questions about climate data, use an agent framework. A framework is a code library that provides the loop from section 3, plus tool handling, memory and subagents. Some widely used ones:

  • Claude Agent SDK (Anthropic) — the same agent loop that powers Claude Code, as a Python or TypeScript library.
  • OpenAI Agents SDK — agents, tools and "handoffs" between agents, in Python or TypeScript.
  • Google Agent Development Kit (ADK) — agents built around Gemini models, with multi-agent support.
  • LangGraph — describes an agent workflow as a graph of steps, and works with many model providers.

The ideas carry over directly. The instructions become a string in code, the tools become Python functions, and a subagent becomes an agent registered as a tool of another agent.

#Part 4 — Make it your own

#15. Adapting the template

  1. Download the template and unzip it into a new project folder.
  2. Rewrite AGENTS.md: what the project is, the folders, the environment, and the Always/Never rules.
  3. Keep the agents you need. Delete the rest. In each one, rewrite the description first, then the procedure and the output format.
  4. Replace the data skill. Swap era5-download for the data source in use: CMIP6, Landsat, station records, model output.
  5. Test each agent alone on a small task before running the full pipeline.
  6. Add rules as problems appear. When an agent makes the same mistake twice, add one line to AGENTS.md, the skill or the agent file.

Example: switching to CMIP6 precipitation projections.

  • AGENTS.md: change the question to "change in summer precipitation by 2050 under SSP2-4.5", and list the models.
  • New skill cmip6-access/: how to search and download from ESGF or a cloud catalogue, variable names (pr in kg m-2 s-1), and the reminder to multiply by 86400 to get mm/day.
  • netcdf-conventions: already covers calendars, which matter more for CMIP6 (noleap, 360_day).
  • data-qc and results-reviewer: no change needed.
