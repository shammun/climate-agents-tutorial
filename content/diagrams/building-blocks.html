📋 Project rules — the constitution of your project
  • Loaded at the very start of every session, before any agent runs
  • Sets tone, file naming conventions, what agents must never do
  • Cannot be overridden by individual agents — it is the global law
  • Keep it short (<100 lines) and absolute — no "usually" or "try to"

📋
1. Project rules
AGENTS.md · CLAUDE.md · GEMINI.md
  • briefing sheet for the whole project
  • sets tone, constraints, file conventions
  • every agent reads this at the start
⏰ loaded: every session, every agent

Think of it as the employee handbook — everyone reads it on day one, every session, with no exceptions. For a climate data project, it typically contains:

## Project rules (CLAUDE.md)

Never delete files in data/raw/ — treat them as immutable.
All figures must be saved to figures/
  with an ISO-date prefix: YYYY-MM-DD_name.png
Use CF conventions for all NetCDF output.
Return structured JSON in the final answer
  so other agents can parse your result.
When a QC check returns FAIL, stop and report
  — do not try to fix or work around it.
✅ Good rules
  • Absolute: "Never overwrite raw data"
  • Short: one clear sentence each
  • Structural: naming, paths, formats
  • Universal: apply to ALL agents
❌ Bad rules
  • Vague: "Try to be careful with data"
  • Domain-specific: belongs in an agent def
  • Long paragraphs — agents miss them
  • Contradictory rules

These rules cannot be overridden by individual agents — they are the constitution of your project. Write them once and leave them alone.

💡 Keep project rules short and absolute. If a rule has exceptions, it doesn't belong here — put it in the agent definition instead.

🤖 Agent definitions — specialist job descriptions
  • One file per specialist agent (data-fetcher, climate-analyst, figure-maker…)
  • Frontmatter: name, description, tools list, model, skills to load
  • Body: the agent's specific instructions — what to do and how
  • Loaded only when that specialist is called — not at startup

🤖
2. Agent definitions
.claude/agents/*.md · .codex/agents/*.toml
  • one specialist per file: role, tools, model
  • each has a name, description, tools list
  • keeps specialists focused and testable
⏰ loaded: only when that agent is delegated to

Think of it as a job description — written once, re-used every time that specialist is needed. The file has two parts separated by ---:

## .claude/agents/data-fetcher.md

name: data-fetcher
description: Downloads ERA5 reanalysis via the CDS API
             for a caller-specified date range and domain
model: claude-sonnet-5-5
tools: [bash, write_file]
skills: [era5-download, netcdf-conventions]
---
You download ERA5 monthly 2m temperature (t2m) for the
date range and domain the caller specifies.

Always save to data/raw/era5/t2m_YYYY.nc.
Never overwrite an existing file — check first with bash.
Report the list of downloaded files in your final answer.
Frontmatter fields
  • name: short slug (used to delegate)
  • description: how the router picks it
  • tools: exact list, nothing extra
  • skills: pre-loaded skill files
  • model: override per specialist
Body best practices
  • Start with the agent's core job in one line
  • List what it reads and what it writes
  • Specify output format (JSON, file path)
  • Name the edge cases it must handle

The frontmatter (above ---) is machine-readable. The body (below) is the LLM's instruction manual. Claude reads both when delegating to this specialist.

💡 The description field is what Claude reads to decide which agent to delegate to — make it precise and distinctive. Avoid generic descriptions like "handles data."

🔧 Skills — reusable instruction packages
  • A skill is a Markdown file (+ optional helper scripts) for one specific capability
  • Not loaded at startup — only when an agent explicitly invokes it
  • Shared across projects: write era5-download once, use it everywhere
  • Lazy loading saves tokens — agents that don't need it pay zero cost

🔧
3. Skills
.claude/skills/<name>/SKILL.md
  • reusable manual + optional helper scripts
  • one skill teaches one capability
  • examples: era5-download, netcdf-conventions
⏰ loaded: only when explicitly invoked

Add skills: [era5-download] to an agent's frontmatter. When that agent starts, the SKILL.md loads — it might contain 200+ lines of expert knowledge:

## .claude/skills/era5-download/SKILL.md

# ERA5 download skill

## Authentication
1. Create a free account at cds.climate.copernicus.eu
2. Copy your UID and API key to ~/.cdsapirc:
   url: https://cds.climate.copernicus.eu/api/v2
   key: <UID>:<API-KEY>

## Variable name mappings
t2m   → '2m_temperature'
u10   → '10m_u_component_of_wind'
v10   → '10m_v_component_of_wind'
tp    → 'total_precipitation'

## Helper scripts included:
  download_era5.py     — single-variable downloader
  check_cds_queue.py   — monitor pending requests
Skill anatomy
  • SKILL.md — instructions + examples
  • Helper .py scripts (optional)
  • Config templates (optional)
  • Test cases (optional)
When to make a skill
  • Specialised API (CDS, ERDDAP, NOAA)
  • Domain conventions (CF, NetCDF, GRIB)
  • Shared plotting style guide
  • Anything >2 agents would need

The skill author maintains it once; every agent that lists it gets the latest version automatically. Update the skill, and all agents immediately benefit.

💡 Skills are reusable across projects. A well-written era5-download skill serves a dozen different projects with no changes — write it once, share it everywhere.

🔒 Permissions — the safety net that never sleeps
  • Enforced by the harness before every tool call — agents cannot bypass this
  • allowedTools: only listed tools are callable, all others are blocked
  • blockedPaths: no agent can touch data/raw/ even if it tries
  • Even a buggy or misbehaving agent cannot break these hard limits

4. Permissions
.claude/settings.json
  • hard limits no agent can override
  • controls allowed tools and blocked paths
  • applied before every tool call, always
⏰ applied: always, before every tool call

The permissions file is the safety net — even a rogue agent can't break these hard limits. It is checked before the tool call runs, not after:

## .claude/settings.json

{
  "allowedTools": [
    "bash", "read_file", "write_file", "python"
  ],
  "blockedPaths": [
    "data/raw",
    "~/.ssh",
    "~/.aws"
  ],
  "maxConcurrentAgents": 4,
  "requireApprovalFor": [
    "bash(rm .*)",
    "bash(git push.*)"
  ]
}
blockedPaths use cases
  • data/raw — protect raw data
  • ~/.ssh — block credential access
  • production/ — block live systems
  • billing/ — protect financial data
requireApprovalFor
  • Destructive bash commands
  • Git push to protected branches
  • API calls that cost money
  • Database DELETE or DROP

The blockedPaths setting prevents any agent from modifying raw data, even if it tries. This is enforced by the harness before the tool call runs — the agent never even gets to attempt it.

💡 Always block your raw data directory. It's the best insurance against an agent accidentally overwriting a 50 GB download that took hours to fetch.
⚠️ What if permissions are too strict? Agents will report "tool not allowed" and stop. Start with a wide allowlist, then tighten it once the pipeline works. Never add write_file to a read-only reviewer — that's what blockedPaths is for.
