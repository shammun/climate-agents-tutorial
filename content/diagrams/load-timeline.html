1. Session starts
  • CLAUDE.md / AGENTS.md loaded (full text)
  • name + description of every defined agent
  • name + description of every skill
  • ⚡ Keeps startup fast — summaries only

CLAUDE.md is loaded first — it sets global rules every agent must follow: file conventions, tone, what not to do. Then every AGENTS.md entry is scanned: only the name: and description: fields load, not the full body.

This keeps startup lightweight. Skill files are not read at all yet — only their names and one-line descriptions.

2. Task delegated to an agent
  • agent gets a fresh, empty context
  • agent body (AGENTS.md entry) + project rules
  • skills listed in skills: are preloaded
  • 🧩 Fully isolated — siblings can't interfere

When Claude decides to delegate, it creates a fresh context — the subagent sees no memory of the parent conversation. It receives:

(1) The full text of its own AGENTS.md entry
(2) CLAUDE.md project rules
(3) Any skills listed in its skills: field

The subagent's tools are limited to exactly what's declared in tools:. Example: if tools: [read_file, python], only those two tools are available — bash is blocked even if the harness supports it.

💡 Isolation is a feature: a subagent can't accidentally overwrite a sibling's output.

3. A skill is invoked
  • full SKILL.md text loads at that moment
  • helper scripts run on demand
  • keeps context lean until actually needed
  • 💰 Saves tokens — no cost until needed

A skill is triggered by a line in AGENTS.md like skills: [era5-download]. The full SKILL.md text loads at that moment — it might be 200 lines of detailed ERA5 API instructions and helper scripts.

This lazy loading keeps per-agent cost low: a data-fetcher pays for the era5-download skill, but a results-reviewer never does.

💡 A well-written skill file can replace pages of agent instructions — write it once, reuse across all projects.

4. Agent finishes
  • only the final answer returns
  • intermediate steps stay inside the agent
  • caller never sees the working context
  • 🔒 Private by default — clean outputs

The subagent's entire working context — every tool call, every file read, every intermediate thought — is discarded. Only its last assistant message returns to the parent.

This is why subagent instructions should ask for structured output:

"Return JSON: {status, files_written, warnings}"

That structured reply is all the parent ever sees — make it count.

💡 Think of a subagent like a function call: inputs in, one clean result out.
